# Source Reconciliation

This prototype preserves the three supplied pipeline files as its source of truth. The corrections below are additive wrappers, explicit UI disclosures, and database/ML components; the source scripts' core logic is not silently replaced.

| # | Issue in supplied materials | Reconciliation and implementation location |
|---|---|---|
| 1 | Spatial scope differs: Python raster ROI approximately 20 km / `dist=20000`; Java downloader URL ends `/nagpur/5km_radius/`. | The raster and street pipeline uses the Python coordinates `[78.89, 20.96, 79.29, 21.33]` and `dist=20000` as canonical. `GisImageDownloader.java` remains unchanged and is only a user-triggered, visibly warned legacy/fallback action. It is not treated as a matching 20 km dataset. |
| 2 | The source dataset builder selects columns into a new DataFrame and drops the geometry. | Keep `scripts/2_build_real_dataset.py` unmodified. The additive `scripts/build_dataset_patched.py` wrapper is responsible for retaining edge geometry and appending exactly `geometry_wkt`, `start_lat`, `start_lon`, `end_lat`, and `end_lon` to the source feature columns. If the graph/raster prerequisites are unavailable, the wrapper fails visibly instead of fabricating real geometry. |
| 3 | `pm` is hardcoded to `65.0`, so the feature has no variance. | The UI and explainability panel display `PM is a constant placeholder (65.0)` and a `Constant input` chip whenever PM appears among model inputs. It is not described as a measured sensor observation or an independently discriminative factor. |
| 4 | The supplied scripts contain AHP scoring, not a trained ML model. | The provided AHP suitability stays visible as a transparent reference. A separate `backend/ml/` layer implements baseline regression, Random Forest, XGBoost classifier/regressor, persisted model artifacts, predictions, model-run metrics, and explanations. |
| 5 | AHP `composite_suitability_score` is suitability (higher is better/cooler), while report HRI is risk (higher is worse). | Preserve the source formula and explicitly derive `risk_raw = 1 - composite_suitability_score` before classification. The overview, detail panels, methodology page, and explanation identify this inversion. |
| 6 | The report is ward-level; the scripts produce road-edge records. | Keep edges as the base layer, with ward summaries and a Street/Ward view. PostGIS schema and spatial aggregation use `ST_Intersects`; the ward output includes mean, max, and p90. Real CSV geometry is assigned in batches to each intersecting non-demo official ward before ward-level training; if polygons/geometry are missing, the model route fails clearly rather than inventing a ward ID or training edge-by-edge. The SQLite preview adapter is only for an offline seedable demo and is labeled synthetic. |
| 7 | A 20 km ROI export at 10 m NDVI can exceed Earth Engine/geemap request limits (roughly 32/50 MB). | The pipeline runner checks outputs and surfaces export-size/download failures with a bounded tile-download/GeoTIFF-mosaic fallback or actionable guidance; Earth Engine Drive export is not configured. It never marks missing or partial GeoTIFFs as successful. The original downloader stays unchanged. |
| 8 | Earth Engine authentication is interactive in the source script. | Run pipeline actions as asynchronous subprocess jobs with timestamped logs and queued/running/success/failed states. The UI explains how to configure cached or service-account credentials and surfaces a concise auth failure instead of only showing a traceback. No Earth Engine credentials are included in source control. |
| 9 | Report Chapter 5 values are explicitly illustrative. | Do not copy report example numbers into the dashboard. Metrics are returned by `/api/metrics` from recorded training/evaluation runs; any run using seed data carries `DEMO DATA` provenance. The global footer says Chapter 5 illustrations are replaced by endpoint output and the provenance stays visible. |
| 10 | The report mentions ESP32/MQTT, but none of the three supplied scripts implements IoT. | Add a paho-mqtt simulator publisher and a subscriber on `nagpur/wards/{ward_id}/sensors` that persists readings and invokes the same threshold/alert ingestion path as the UI. Duplicate deliveries keyed by ward/device/timestamp are ignored. Synthetic readings are labeled `DEMO DATA`; an unverified broker payload does not establish physical-device identity. SMS/email delivery remains a visibly labeled stub with no gateway configured. |

## Source facts retained

The four raster paths are `data/raw/nagpur_lst.tif`, `data/raw/nagpur_ndvi.tif`, `data/raw/nagpur_slope.tif`, and `data/raw/nagpur_pop.tif`. The source feature names are `lst`, `ndvi`, `pm`, `population`, and `slope`. The supplied five weights are LST `0.35`, NDVI `0.25`, PM `0.20`, population `0.10`, and slope `0.10`; their exact formula remains in the preserved builder and on the methodology page.
