## 2. Concrete gaps or defects

- **High — Map popups omit required explanations.** Ward map popups show scores and a basis statement, but no numeric contribution breakdown or plain-English “why”; street popups show edge ID, ward, LST and NDVI without a risk score or explanation. The detail page has a separate explanation panel, but that does not satisfy the specified explanation in every ward/street popup. `frontend/assets/js/map.js:51-63, 151-160`.
- **High — Real-data training/prediction is edge-level and predictions are not persisted.** For a real CSV, `_build_dataset()` returns per-edge records with `sample_id`, not ward aggregates or `ward_id`: `backend/ml/train.py:166-177`. `predict_all()` consequently emits `ward_id=None` for those rows: `backend/ml/predict.py:100-115`; the prediction route skips rows without `ward_id` before inserting into `risk_scores`: `backend/routes/model.py:97-105`. Thus the specified ward-aggregated real-data training and persisted predictions do not work through this path.
- **Medium — Focus outline falls below non-text contrast.** The amber focus outline is `#F59E0B` (`frontend/assets/css/theme.css:65`), which is only **2.15:1** against white (and 2.05:1 against the page background), below the 3:1 contrast target for a visible control indicator. The supplied audit checks text foreground/background pairs, not outline contrast (`frontend/assets/js/contrast-audit.js:15-22`), so a zero text-pair count would not establish compliance for this defect.
- **Medium — MQTT subscriber is not an application ingestion path.** Its `on_message` callback only prints received topic/payload; it does not persist `sensor_readings` or trigger the alert flow. `backend/mqtt_simulator.py:78-83`. The separate `/api/alerts/simulate` endpoint does persist synthetic readings and create alerts, but does not connect the live subscriber to that flow (`backend/routes/alerts.py:48-65`).
- **Medium — Explanation API can mislabel real data as demo.** The ward explanation response hard-codes `demo: True` and `provenance: "demo_synthetic"`, regardless of source, at `backend/routes/wards.py:291-293`. The metrics and alert UI also renders a DEMO badge for any nonempty provenance rather than only demo provenance (`frontend/assets/js/ui.js:75, 87`), so real-source runs can be mislabeled.
- **Medium — Pipeline idempotency is only partial.** Calls with identical arguments coalesce while active, but completed runs are not reused unless the caller supplies an explicit key; the UI submits no such key. Repeated train/predict runs can append model-run and risk-score records. `backend/pipeline_runner.py:351-381`; UI dispatch: `frontend/assets/js/ui.js:125`.
- **Medium — The live instance has no real raster inputs.** Its health response reports 0/4 GeoTIFFs and SQLite, not PostGIS. Demo mode works, but no real raster-derived dataset or live PostGIS aggregation is available in this running instance.
- **Low — TODO status conflicts with implemented-state claims.** Every checklist item remains unchecked in `TODO.md:3-56`, despite the implementation and other docs describing completion; the file does not distinguish incomplete items from completed work.
